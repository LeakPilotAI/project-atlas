# Disposable offline-backup ingestion — 2026-10-24

## Implemented boundary

`DisposableRecovery.restore_offline` in `scripts/volume_inspector/financial_recovery.py` restores an authenticated disposable backup set without accepting or opening original source, projection or report directory paths. This extends the existing archival protocol; it does not introduce a new financial engine or a writable restored FS2/FS3 store. FS1 transition/replay, independent financial audit and historical daily-report audit remain the financial authorities within this engineering scope. No original financial records were opened, migrated or rewritten.

Inputs are explicit: backup root, versioned backup manifest, independently supplied source-cut receipt, new destination, stable recovery identity and injected recovery authority. There are no default paths, operational composition hooks, backup issuer, credentials, clock or enrollment. The manifest and receipt are untrusted data until the injected authority authenticates their exact binding. A file's digest, a JSON receipt, a test object or a locally generated pin does not itself supply authority.

## Versioned contracts

| Contract | Exact purpose and binding |
|---|---|
| `FS_OFFLINE_BACKUP_V1` | Explicit backup identity and native backup-root identity; original account enrollment and complete acknowledged current cut; exact bounded file inventory. Each row supplies role, original leaf, original native ID/digest, backup leaf and separately enrolled physical backup ID/digest. The manifest is externally supplied; this implementation does not issue operational backups. |
| `FS_BACKUP_CUT_V1` | Binds the entire backup-manifest digest, enrollment digest, current source/report pin digest, high-water, generation and ACKNOWLEDGED status. Custody must authenticate the original cut and establish whether that cut remains permitted for recovery. |
| `FS_OFFLINE_RECOVERY_REQUEST_V1` | Stable recovery identity, original enrollment/current cut, authenticated source-cut receipt, backup identity/root. The source-cut receipt commits to the exact manifest; authority must retain that manifest/cut binding, not accept caller-created hashes as approval. |
| `FS_RECOVERY_ARCHIVE_V2` | Preserves original immutable bytes and original logical references, with separate new destination-root and creation-handle file bindings. Original source pin identities are not rewritten or relabeled as destination identities. |
| Existing `FS_RECOVERY_RECEIPT_V1` / `FS_RECOVERED_RESEARCH_VIEW_V1` | Receipt refers to the exact archive commit; verified archive remains read-only, `startup_authorized=false`, `financial_writes_authorized=false`. The existing V1 archival format continues to read and restore through its original interface. |

The same authority lease/check/accept/validate interface is reused. The lease must authenticate backup identity, manifest digest and original cut against independent current custody; reject stale, rolled-back, UNKNOWN, superseded, expired or unauthorized recovery; cover the backup namespace during ingestion; and enforce durable single-use/CAS acceptance for the exact new descriptor and commit identity. It must approve the new destination mapping, not just the old source cut. The implementation supplies none of that operational authority. In-memory fixture custody is labeled synthetic and never accepted operationally.

## Verification and publication

1. Validate bounded manifest schema, exact receipt binding, stable recovery ID and nonoverlapping backup/destination. Require injected authority and verify its lease before native backup reads or destination allocation. Bad manifest, untrusted custody or mismatched receipt cannot publish an archive.
2. Open the existing backup root with the reviewed native read-only primitive. Verify its enrolled native identity; each backup file must match its own physical identity before payload access, exact protected DACL, single-link and bounded-length rules. Then verify original-byte digest and canonical strict JSON. Duplicate logical records, repeated/case-aliased physical leaf names and extra/missing namespace entries refuse.
3. Reconstruct and verify original logical evidence directly from backed-up bytes: inception/account/policy/epoch; source and report pin schemas; exact typed revision/high-water; all FS2 intent/record/commit/ack predecessor references; FS3 projection context, deterministic prefix, root and intent/view/ack links; report predecessor and document identity. Reject missing required acknowledgements, incomplete projection history, unexpected files and unsupported versions.
4. Reuse FS1 deterministic replay and independent arithmetic. Reconcile projected state and each original historical report against its original committed prefix, scope and source identities. Require a current report at the acknowledged high-water. Preserve legitimate open overnight positions and INCOMPLETE intraday reporting; neither implies liquidation or clean lifecycle acceptance.
5. Recheck authority. Exclusively create the new destination, flush immutable intent, copy byte-identical records, capture identity from each original destination creation handle, re-read bindings, publish the versioned mapping/commit and obtain independent durable acknowledgement. A short write, incomplete copy or commit-before-ack failure leaves retained incomplete evidence and cannot return a successful receipt. Same-destination retries do not overwrite; accepted recovery IDs cannot be reused through compliant external custody. No financial event or callback is executed by this process.
6. Recovered reads need neither original directories nor backup media. They check new native identities, exact namespace, authority before/after, byte preservation and original logical chains/replay/report audit again. They expose no financial execution interface, store initialization, UNKNOWN clearing, report publication, provider refresh or startup permission.

Bounds remain explicit: at most 1,027 inventory files; each native file at most 65,536 bytes; manifest and restored commit descriptor at most 65,536 bytes. A long history can exceed descriptor capacity before the file-count bound; that attempt refuses and retains any created evidence rather than truncating, rotating or fabricating success. General archival retention/large-media scaling is not operationally accepted.
